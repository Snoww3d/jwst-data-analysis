# Spec: Python auth lockout parity + admin unlock

- **Status:** draft for human danger review; implementation authorized by #1186 dispatch
- **Intent:** [#1186](https://github.com/Snoww3d/jwst-data-analysis/issues/1186) (owner-approved CEO/eng review in the issue thread)
- **Prerequisite:** #1991 (Python auth foundation, merged as #1998)
- **Date:** 2026-09-18

## Summary

Port the .NET failed-login counter and timed lockout (#1096) into the Python login
path, using the same `FailedLoginAttempts` / `LockedUntil` user fields so documents
behave identically under either backend during cutover. Add the two admin endpoints
the .NET side never got, so recovering a locked account no longer needs a manual
Mongo edit.

## Requirements

| # | Requirement | Verified by |
|---|-------------|-------------|
| R1 | Wrong password on an active, unlocked account increments `FailedLoginAttempts`; the attempt reaching the threshold (default 5) sets `LockedUntil` = now + 15 min | unit + real-Mongo tests |
| R2 | Active lockout rejects login with the generic 401 and does not count further attempts | unit + real-Mongo tests |
| R3 | Expired lockout restarts the counter at zero before evaluating the attempt | unit + real-Mongo tests |
| R4 | Successful login resets the counter in the same conditional write that stores the new tokens | unit + real-Mongo tests |
| R5 | Concurrent failures are all counted (atomic update, no read-modify-write) | real-Mongo concurrency test |
| R6 | `GET /api/auth/admin/lockout-status/{user_id}` → `{userId, username, isLocked, failedLoginAttempts, lockedUntil}`; nothing else from the user document | exact-key allowlist test |
| R7 | `POST /api/auth/admin/unlock/{user_id}` resets counter, nulls `LockedUntil`, logs acting admin id, idempotent, returns the post-unlock status | unit + real-Mongo tests |
| R8 | Non-admin → 403, missing token → 401, unknown or malformed id → 404, Mongo failure → sanitized 503; all behind `PYTHON_AUTH_ENABLED` | route tests |
| R9 | Locked → unlock → login succeeds end to end | real-Mongo test |

## Approach

Mirror `AuthService.LoginAsync` ordering: look up the user, always run bcrypt
(timing normalization), reject inactive users, reject an active lockout without
counting, reset an expired lockout, then count a failure or issue tokens.

Persistence lives in `app/db/users.py`:

- `record_failed_login` — a single `find_one_and_update` with an update pipeline:
  `FailedLoginAttempts = ifNull(count, 0) + 1`, then `LockedUntil = count >= max ?
  lockedUntil : existing`. Atomic, so parallel failures cannot lose increments
  (the .NET `$inc` has the same property; the pipeline adds the threshold check
  server-side instead of using a stale in-memory count).
- `reset_lockout` — `$set` counter 0 and `LockedUntil` null (the .NET unset and a
  null both deserialize to `null` in `User.LockedUntil`).
- `by_id` — malformed ObjectIds return `None` (→ 404), never a driver error.

The success-path reset rides on the existing `save_login` compare-and-set, so a
concurrent password/role/lock change still voids the login.

Settings extend `TokenSettings` (mirroring .NET `JwtSettings`):
`JWT_MAX_FAILED_LOGIN_ATTEMPTS` (5, 1–100) and `JWT_ACCOUNT_LOCKOUT_MINUTES`
(15, 1–1440). Out-of-range values fail closed with the existing 503.

Admin routes use `require_role("Admin")` declared before the service dependency,
so authorization is decided before any database access. They live under the
same `AuthRoute` wrapper (enable gate, sanitized errors, `no-store`).

### Alternatives rejected

| Option | Why not |
|--------|---------|
| Read count, compute lock in Python, `$set` both | Lost updates under concurrent failures |
| `$inc` then a second write to lock | Two round trips and a window where the threshold is passed but not locked |
| Return 200 with empty body for unknown id | Silent failure in admin tooling (eng review decision) |
| snake_case response keys as written in the issue | Every auth DTO uses the camelCase .NET wire contract; `AuthModel` generates aliases |

## Data model and API changes

No new fields or collections. Response keys are camelCase to match the auth wire
contract. `lockedUntil` is ISO-8601 UTC (`Z`) or `null`. `unlock` returns the
same shape as `lockout-status` (after reset).

## Failure modes

| Failure | Detected how | Behaviour |
|---------|--------------|-----------|
| Unknown user / wrong password / locked / inactive | Service checks | Same generic 401 |
| Unknown or malformed `user_id` | `by_id` returns None | 404 `User not found` |
| User deleted between lookup and unlock | `reset_lockout` matched 0 | 404 |
| Non-admin / no token | `require_role` | 403 / 401 before DB |
| Mongo unavailable | Driver exception | Sanitized 503 |
| Bad lockout settings | `TokenSettings.from_env` | 503, no writes |

## Flagged concerns

- [ ] Touches `processing-engine/app/auth/**` and `processing-engine/app/db/**`
  (danger zones): owner review and the Danger Zone label are required at the
  final revision.
- [ ] Inherited from the .NET design: anyone who knows a username can lock that
  account for 15 minutes by guessing wrong 5 times. The admin unlock is the
  mitigation; rate limiting remains an edge concern for the cutover.
- [ ] Failed logins on real accounts perform one or two extra writes that unknown
  usernames do not, a small timing difference also present in .NET.
- [ ] Admin role comes from the signed access token, so a demoted admin keeps
  access until the token expires (≤ 60 min), same as every other role check.

## Open questions carried forward

None. Email notification, frontend admin UI, bulk unlock and force-lock are out of
scope per the issue; production activation remains the later ADR 0001 cutover.
